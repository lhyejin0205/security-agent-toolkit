  - IPv4 주소: 192.168.100.127
  - MAC 주소(물리적 주소): D8-BB-C1-40-37-29
  - 기본 게이트웨이: 192.168.1.1

### 문제 3-3 · 게이트웨이까지 `ping`

- 게이트웨이까지 평균 · 2-2 의 `8.8.8.8` 평균:
 - 게이트웨이(192.168.1.1) 평균: 0ms (<1ms)
  - 8.8.8.8 평균: 35ms
- 게이트웨이까지가 더 짧은 이유는 무엇인가요?
  - 답:게이트웨이는 같은 내부망(LAN)에 있는 공유기라서 한 번만 거치면 도착하지만, 8.8.8.8은 인터넷 바깥의 서버라 공유기를 지나 통신사 망과 여러 라우터를 거쳐야 하므로 거리와 경유 횟수가 많아 시간이 더 걸립니다.
  - 근거: 게이트웨이는 TTL=64(라우터를 거치지 않음), 8.8.8.8은 TTL=115로 응답했습니다.

### 문제 3-4 · ARP 캐시 보기 — `arp -a`

- 게이트웨이 줄의 MAC 주소 · 유형: 192.168.1.1 → 00-10-f3-a3-fc-96 · 동적
- 🔍 ARP 는 무엇을 알아내려고 쓰나요? 내 결과의 게이트웨이 줄을 예로 들어 설명합니다.
  - 답: 같은 네트워크 안에서 IP 주소에 해당하는 장비의 MAC 주소를 알아내려고 씁니다. PC가 게이트웨이(192.168.1.1)로 보내려면 이더넷 프레임에 목적지 MAC이 필요하므로, "192.168.1.1의 MAC이 뭐예요?"라고 같은 망 전체에 물어보고, 게이트웨이가 자기 MAC으로 답하면 그 대응을 ARP 캐시에 잠시 저장해 둡니다. 물어봐서 알아낸 항목이라 유형이 `동적`입니다.

### ⭐ 도전 3-5 · 주소 모양으로 IP 와 MAC 구별하기

- 출력 첫 줄: 192.168.0.15

### 이 교시에 새로 안 것

- 이 교시에서 새로 알게 된 것:
 - `ipconfig /all`로 내 PC의 IPv4 주소, MAC 주소(물리적 주소), 기본 게이트웨이를 한 번에 확인할 수 있다. 서브넷 마스크가 /16(255.255.0.0)이면 192.168.100.127과 게이트웨이 192.168.1.1이 같은 네트워크로 계산된다.
  - 게이트웨이(같은 내부망)는 0ms, 8.8.8.8(인터넷 바깥)은 35ms로 응답해서, 거쳐야 하는 장비가 많을수록 왕복 시간이 길어진다. 게이트웨이 ping이 성공하면 문제가 내부망 바깥에 있는지 안에 있는지 나누는 기준이 된다.
  - TTL은 장비마다 초기값(64, 128, 255 등)이 달라서, 서로 다른 장비의 TTL을 직접 비교해 거리를 판단하면 안 된다.
  - ARP는 같은 망에서 "이 IP의 MAC이 뭐예요?" 하고 물어 IP와 MAC을 연결하는 방법이고, 그 결과를 저장한 표가 ARP 캐시(`arp -a`)다. 게이트웨이 MAC(00-10-f3-a3-fc-96)이 평소와 달라지면 ARP 스푸핑을 의심할 수 있다.
  - 주소 문자열을 `split()`으로 나눈 조각 개수(IP는 `.`으로 4개, MAC은 `-`로 6개)로 종류를 구별하는 파이썬 함수를 만들었다. 다만 개수만 세기 때문에 값의 범위까지는 검사하지 못한다.

## 5교시 · TCP

### 문제 5-1 · 직접 실행해 보기

- 출력 세 줄:- `True`, `False`, `443`
- 탐지 코드에서 플래그를 `==` 로 검사하면 어떤 일이 생기나요? 둘째 줄을 근거로 설명합니다.
  - 답: 
  - 탐지 코드에서 플래그를 `==` 로 검사하면 어떤 일이 생기나요?
  - 둘째 줄이 `False`로 나온 것처럼, `==` 는 `["SYN", "ACK"]` 리스트 전체를 `"ACK"` 문자열과 비교하기 때문에 `ACK` 플래그가 켜져 있어도 항상 `False`가 됩니다.
  - 패킷의 플래그는 여러 개가 한 리스트에 함께 들어오는 경우가 많습니다. 그래서 `==` 로 검사하면 SYN이나 FIN이 들어 있는 패킷도 놓치고, 탐지 코드가 아무것도 잡지 못합니다.
  - 리스트 안에 특정 플래그가 있는지 확인하려면 `in` 을 사용해야 합니다.

### 문제 5-2 · TCP 일까 UDP 일까

- ① ~ ⑤ 가 각각 TCP · UDP · ICMP 중 무엇인지: ① TCP · ② UDP · ③ TCP · ④ UDP · ⑤ ICMP
- ① 사진 파일 보내기가 TCP 인 이유는 무엇인가요?
  - 답: 사진 파일은 데이터가 빠지거나 순서가 바뀌면 파일이 손상될 수 있습니다. TCP는 도착 여부를 확인하고 빠진 데이터를 다시 보내므로 사진 파일을 정확히 전달하는 데 알맞습니다.

### 문제 5-3 · 세 번의 순서 맞히기

- 세 패킷의 순서와 방향: (나) `[SYN]` 내 PC → 서버 · (다) `[SYN, ACK]` 서버 → 내 PC · (가) `[ACK]` 내 PC → 서버
- 🔍 연결을 맺을 때는 세 번인데, 끝낼 때는 왜 네 번인가요?
  - 답: 연결을 맺을 때 서버는 연결 요청을 받은 확인(ACK)과 자기 쪽 연결 요청(SYN)을 한 패킷으로 함께 보낼 수 있어 세 번입니다. 연결을 끝낼 때는 양쪽이 각자 보낼 데이터가 끝났음을 알리고 확인해야 하므로, 각 방향의 종료 알림(FIN)과 확인(ACK)이 따로 오가 네 번입니다.

### 문제 5-4 · 같은 서버로 간 두 연결은 무엇이 다른가

- 두 연결에서 같은 것 · 다른 것: 프로토콜(TCP)·내 IP(192.168.0.15)·서버 IP(142.250.196.110)·서버 포트(443)는 같고, 내 쪽 임시 포트는 51234와 51240으로 다릅니다.
- 같은 서버로 간 두 연결을 무엇으로 구별하나요?
  - 답: 내 PC의 출발지 포트(임시 포트)가 다르므로 두 연결을 구별할 수 있습니다.

### 이 교시에 새로 안 것

- 이 교시에서 새로 알게 된 것: 파일처럼 정확한 전달이 중요한 통신에는 TCP, 빠른 실시간 통신에는 UDP를 주로 쓰고, `ping`은 ICMP를 사용한다는 것을 알았습니다. TCP 연결은 SYN·SYN/ACK·ACK 순서로 시작하며, 연결은 내 임시 포트로 구별할 수 있습니다.

- 전체 `Packets` · `dns` · `udp` · `tcp.port == 443` 의 `Displayed`: 전체 2018 · 필터별 수는 Wireshark에서 확인
- 필터를 걸어도 `Packets` 는 그대로인데 `Displayed` 만 바뀌는 이유는 무엇인가요?
  - 답: 표시 필터는 캡처된 패킷을 지우지 않고 조건에 맞는 패킷만 화면에 보여 줍니다. 그래서 전체 `Packets` 수는 그대로이고, 현재 보이는 패킷 수인 `Displayed`만 필터에 따라 바뀝니다.

### 이 교시에 새로 안 것

- 이 교시에서 새로 알게 된 것: Wireshark에서 패킷의 Source와 Destination을 보면 통신 방향을 알 수 있고, Ethernet·IP·TCP 헤더를 펼쳐 MAC 주소, IP 주소, TTL, 포트, 플래그를 확인할 수 있습니다. 표시 필터는 패킷을 지우지 않고 조건에 맞는 것만 보여 줍니다.

## 최종 분석 — 7교시에 완성합니다

> 오늘 잡은 **내 HTTP 연결 하나**를 처음부터 끝까지 정리합니다. 위에서 적은 6-3 · 7-1 · 7-2 의 답을 다시 보며 씁니다.

### 1. 연결이 열리는 순간 — 3-way handshake

- 세 줄의 Source → Destination 과 Info: 내 PC → 서버 `[SYN]` · 서버 → 내 PC `[SYN, ACK]` · 내 PC → 서버 `[ACK]` (실습 캡처의 주소·임시 포트는 기록하지 않음)
- 세 줄이 오간 뒤 두 컴퓨터는 어떤 상태가 되나요?
  - 답: TCP 연결이 성립해 두 컴퓨터가 데이터를 주고받을 수 있는 `ESTABLISHED` 상태가 됩니다.

### 2. 패킷 하나를 열어 본 값 — 6-3

- 출발지 · 목적지 IP (3층) · TTL · 출발지 · 목적지 포트 (4층): 192.168.100.127 → 140.82.112.22 · TTL 128 · 61646 → 443
- 목적지 포트를 보고 어떤 서비스로 가는 패킷인지 알 수 있나요? 4.1 표를 근거로 설명합니다.
  - 답: 4.1 표에서 443은 HTTPS 서비스에 쓰이는 포트이므로 HTTPS 웹 통신으로 볼 수 있습니다. 다만 포트 번호만으로 실제 통신 내용을 확정할 수는 없습니다.

### 3. HTTP 요청 — 7-2

- 요청 줄에서 그대로 보인 내용: `GET /?q=network_day1 HTTP/1.1`
- 이것이 보안에서 문제가 되는 이유는 무엇인가요?
  - 답: HTTP는 암호화되지 않아 같은 네트워크에서 패킷을 볼 수 있는 사람이 검색어와 요청 내용을 읽을 수 있습니다. 비밀번호나 개인정보를 주고받으면 노출될 수 있으므로 HTTPS를 사용해야 합니다.

### 4. 오늘 하루 정리

- 오늘 배운 것 가운데 가장 중요하다고 생각하는 것과 그 이유: 패킷의 주소·포트와 통신 방향을 살펴보면 연결이 어디서 어디로 가는지 알 수 있고, HTTP처럼 암호화되지 않은 통신은 내용이 노출될 수 있다는 점이 가장 중요합니다. 실제 패킷을 근거로 문제를 판단하고 안전한 HTTPS 사용의 필요성을 알 수 있기 때문입니다.
