## 5교시 · 어제 명령 복습 · 서버 두 대 켜고 접속 기록 구분해 읽기

### 문제 5-1 · 어제와 같은 명령으로 서버 두 대를 켜고 접속 기록을 구분해 읽기

- (가) 내가 `web-three` 와 `web-four` 를 켠 `docker run` 명령 두 개를 붙여 넣어 주세요.
  - 쓸 내용: 윈도는 `MSYS_NO_PATHCONV=1` 부터, 맥북은 `docker run` 부터 친 그대로 두 줄
  - 답:

```
MSYS_NO_PATHCONV=1 docker run -d --name web-three -p 8082:80 -v "$(pwd)/site-three:/usr/share/nginx/html:ro" nginx:1.28
MSYS_NO_PATHCONV=1 docker run -d --name web-four -p 8083:80 -v "$(pwd)/site-four:/usr/share/nginx/html:ro" nginx:1.28
```

- (나) 🔍 `docker ps` 에서 `web-three` 와 `web-four` 줄의 `PORTS` 값을 각각 적어 주세요.
  - 쓸 내용: 「web-three: … / web-four: …」
  - 답: web-three: `0.0.0.0:8082->80/tcp`, `[::]:8082->80/tcp` / web-four: `0.0.0.0:8083->80/tcp`, `[::]:8083->80/tcp`
- (다) 🔍 8082 로 세 번, 8083 으로 한 번 접속했을 때 `docker logs web-three` 와 `docker logs web-four` 의 `"GET / HTTP/1.1"` 줄은 각각 몇 개였고, 왜 그렇게 나뉘나요?
  - 쓸 내용: ① web-three 의 줄 수 ② web-four 의 줄 수 ③ 그렇게 나뉘는 이유(어느 포트로 온 요청이 어느 서버에 기록되는지)
  - 답: web-three은 4개, web-four는 8개였습니다. 8082 포트로 들어온 요청은 web-three의 로그에, 8083 포트로 들어온 요청은 web-four의 로그에 기록됩니다. 브라우저에서 새로고침을 여러 번 해서 안내된 횟수보다 요청이 더 기록됐으며, 304 응답도 GET 요청 한 줄로 셉니다.
- (라) 🔍 `stop` 뒤에 `docker ps` 와 `docker ps -a` 에서 두 서버가 각각 어떻게 보였고, `rm` 뒤에는 어떻게 되었나요?
  - 쓸 내용: 「stop 뒤 ps: … / stop 뒤 ps -a: … / rm 뒤 ps -a: …」
  - 답: stop 뒤 ps: 두 서버 모두 보이지 않음 / stop 뒤 ps -a: web-three은 `Exited (0)`, web-four는 `Exited (137)` 상태로 보임 / rm 뒤 ps -a: 두 서버가 사라지고 기존 hello-world 컨테이너만 남음
- (한 줄) 보안 담당에게 보낼 답을 한 문장으로 적어 주세요.
  - 쓸 내용: 보안 담당이 바로 읽을 수 있는 한 문장(서버를 몇 대 어떻게 켰고 기록이 어떻게 남았는지)
  - 답: 웹 서버 두 대를 각각 다른 포트로 실행해 페이지를 제공했고, 요청 기록은 각 서버의 로그에 따로 남았습니다.
- 이 교시에서 새로 알게 된 것 하나를 적어 주세요.
  - 쓸 내용: 자유롭게
  - 답: `docker stop`은 컨테이너를 멈추고, `docker rm`은 멈춘 컨테이너를 삭제한다는 것을 알게 되었습니다.

## 6교시 · 내 이미지 만들기 (Dockerfile)

### 문제 6-1 · Dockerfile 두 줄을 써서 내 이미지 만들기

- (가) 내가 쓴 Dockerfile 두 줄을 붙여 넣어 주세요.
  - 쓸 내용: Dockerfile 두 줄(`FROM` 줄 · `COPY` 줄)
  - 답:

```
FROM nginx:1.28
COPY site-three/index.html /usr/share/nginx/html/index.html
```

- (나) 🔍 `FROM` 과 `COPY` 가 각각 하는 일을 적어 주세요.
  - 쓸 내용: ① FROM 이 하는 일 ② COPY 가 하는 일
  - 답: `FROM nginx:1.28`은 nginx:1.28 이미지를 바탕 이미지로 지정합니다. `COPY`는 내 PC의 `site-three/index.html`을 이미지 안의 `/usr/share/nginx/html/index.html`로 복사합니다.
- (다) 🔍 5교시와 달리 `docker run` 에 `-v` 가 없는데도 내 화면이 나오는 이유는 무엇인가요?
  - 쓸 내용: ① 어제 파일이 컨테이너에 닿던 방법 ② 오늘 파일이 서버에 있는 위치와 시점
  - 답: 5교시에는 `-v`로 내 PC의 폴더를 컨테이너에 연결해 파일을 제공했습니다. 이번에는 `docker build` 때 `COPY`로 파일을 이미지 안의 nginx 웹 폴더에 넣었기 때문에, 그 이미지로 컨테이너를 실행하면 `-v` 없이도 페이지가 나옵니다.
- (라) 🔍 `docker build` 출력에서 `[2/2] COPY` 줄과 `naming to` 줄을 붙여 넣고, 각각 무엇을 알려 주는지 적어 주세요.
  - 쓸 내용: ① 두 줄 ② 각 줄이 알려 주는 것
  - 답:

```
 => [2/2] COPY site-three/index.html /usr/share/ngin  1.2s
 => naming to docker.io/library/my-nginx:1         0.0s
```

`[2/2] COPY`는 Dockerfile의 두 번째 단계에서 페이지 파일을 이미지에 복사했음을 뜻합니다(터미널 출력에서는 경로가 잘려 보였고, Dockerfile의 전체 대상 경로는 `/usr/share/nginx/html/index.html`입니다). `naming to`는 빌드가 끝나 결과 이미지에 `my-nginx:1`이라는 이름을 붙였음을 뜻합니다. 빌드가 `FINISHED`로 끝났고, 이후 `docker run`으로 해당 이미지의 컨테이너가 실행된 것도 확인했습니다.


## 7교시 · 이미지 버전 다루기 · 되돌리기 · 정리 · 올리기

### 문제 7-1 · 파일을 고쳐 보고, 이미지를 다시 만들어 반영하기

- (가) 파일을 고친 직후 새로 고침했을 때 화면에 무엇이 나왔나요?
  - 쓸 내용: 새로 고침했을 때 보인 화면의 큰 제목
  - 답: 파일을 고친 직후에는 기존 컨테이너가 `my-nginx:1` 이미지를 사용하므로 이전 제목인 `site-three`가 보였습니다. 새 이미지 `my-nginx:2`로 컨테이너를 다시 실행한 뒤에는 `site-three v2`로 바뀌었습니다.
- (나) 🔍 파일을 고쳤는데도 화면이 바뀌지 않은 이유와, 바꾸려면 무엇을 해야 하는지 적어 주세요.
  - 쓸 내용: ① 바뀌지 않은 이유(서버가 보는 파일이 어디 있는지) ② 바꾸려면 할 일
  - 답: 파일은 이미지 안에 복사되어 있고 기존 컨테이너는 만들어질 때 선택한 `my-nginx:1`을 계속 사용하므로, 내 PC의 원본 파일을 수정해도 화면이 자동으로 바뀌지 않습니다. 수정한 파일로 `my-nginx:2` 이미지를 새로 빌드하고, 기존 `my-site` 컨테이너를 삭제한 뒤 새 이미지로 컨테이너를 다시 실행해야 합니다.
- (다) 🔍 5교시의 `-v` 방식과 6교시의 이미지에 넣는 방식은 파일을 고쳤을 때 반영되는 방법이 어떻게 다른가요?
  - 쓸 내용: ① -v 방식의 반영 방법 ② 이미지에 넣는 방식의 반영 방법
  - 답: `-v` 방식은 내 PC의 폴더를 컨테이너에 연결하므로 원본 파일 수정이 컨테이너에 바로 반영됩니다. 이미지 방식은 파일이 빌드 시 이미지 안에 복사되므로, 파일을 수정한 뒤 새 이미지를 빌드하고 새 컨테이너를 실행해야 반영됩니다.

### 문제 7-2 · 이전 버전으로 되돌리고 쓰지 않는 이미지 지우기

- (가) 이전 버전으로 되돌린 뒤 `docker ps` 의 `IMAGE` 칸 값과 브라우저에 나온 제목을 적어 주세요.
  - 쓸 내용: 「IMAGE: … / 브라우저 제목: …」
  - 답: IMAGE: `my-nginx:1` / 브라우저 제목: `site-three`
- (나) 🔍 쓰고 있는 `my-nginx:1` 을 `docker rmi` 로 지우려 했을 때 에러 문구의 핵심과, 어떻게 해결했는지 적어 주세요.
  - 쓸 내용: ① 에러 문구의 핵심 ② 지워지지 않은 이유 ③ 해결한 순서
  - 답: 오류의 핵심은 `container 40986a8f956b is using its referenced image`로, 실행 중인 `my-site` 컨테이너가 `my-nginx:1` 이미지를 사용 중이라 삭제할 수 없다는 뜻입니다. 먼저 사용하지 않는 `my-nginx:2`를 삭제하고, `my-site` 컨테이너를 삭제한 다음 `my-nginx:1`을 삭제했습니다. 마지막 `docker images`에서 두 이미지가 모두 사라지고 `nginx:1.28`과 `hello-world:latest`만 남은 것을 확인했습니다.
- (다) 🔍 이미지에 `:1` · `:2` 같은 태그를 붙여 두면 문제가 생겼을 때 어떤 점이 좋은가요?
  - 쓸 내용: ① 되돌리는 방법 ② 어느 버전이 켜져 있는지 아는 방법
  - 답: 문제가 생기면 이전 버전 태그(예: `my-nginx:1`)로 컨테이너를 다시 실행해 되돌릴 수 있습니다. `docker ps`의 `IMAGE` 칸을 보면 현재 컨테이너가 어떤 버전을 사용 중인지 알 수 있습니다.
- (한 줄) 보안 담당에게 보낼 답을 한 문장으로 적어 주세요.
  - 쓸 내용: 보안 담당이 바로 읽을 수 있는 한 문장(되돌린 일과 정리한 일)
  - 답: 문제가 생긴 v2 대신 `my-nginx:1`로 서비스를 되돌렸고, 컨테이너를 지운 뒤 사용하지 않는 `my-nginx:2`와 `my-nginx:1` 이미지를 정리했습니다.
- 이 교시에서 새로 알게 된 것 하나를 적어 주세요.
  - 쓸 내용: 자유롭게
  - 답: 실행 중인 컨테이너가 사용하는 이미지는 바로 삭제할 수 없으며, 먼저 컨테이너를 삭제해야 이미지를 지울 수 있다는 것을 알게 되었습니다.

### 문제 7-3 · 오늘 만든 것을 깃허브에 올리기

- (가) `git status` 를 쳤을 때 빨간 목록에 줄이 몇 개였는지, 그 가운데 `.env` · `.venv` 가 있었는지 적어 주세요.
  - 쓸 내용: ① 빨간 목록의 줄 수 ② .env · .venv 가 있었는지
  - 답: `Untracked files` 목록에 15개 항목이 있었고, `.env`와 `.venv`는 없었습니다. 이후 `git add .`, `git commit`, `git push`를 순서대로 실행했고 커밋 `7f3a1f9`가 `main` 브랜치에 성공적으로 올라갔습니다.
