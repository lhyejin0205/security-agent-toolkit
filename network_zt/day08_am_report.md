## 2교시 · 도커로 서버 알림 세 건 직접 확인 · 보안 담당에게 답장

### 문제 2-1 · 알림 A 확인 — 서버 두 대로 열려 있는지 재고, 설정 값 · 비밀번호 · 실행 사용자까지 점검하기

- (가) `docker ps` 의 `PORTS` 열에서 두 서버가 각각 어떻게 나왔는지 적어 주세요.
  - 쓸 내용: ① closed-web-8081 의 PORTS 값 ② open-web-8082 의 PORTS 값
  - 답: `closed-web-8081` 은 `127.0.0.1:8081->80/tcp`, `open-web-8082` 는 `0.0.0.0:8082->80/tcp` 와 `[::]:8082->80/tcp` 로 나왔다. 앞 서버는 호스트의 로컬 주소에만, 뒤 서버는 IPv4·IPv6의 모든 주소에 포트를 공개한 설정이다.
- (나) 🔍 `내주소` 로 접속했을 때 `closed-web-8081` 과 `open-web-8082` 의 결과(응답 번호)를 각각 적어 주세요.
  - 쓸 내용: ① closed-web-8081 의 응답 번호 ② open-web-8082 의 응답 번호
  - 답: 내 PC 주소 `192.168.100.127` 로 접속했을 때 `closed-web-8081` 은 연결에 실패해 HTTP 응답 번호를 받지 못했다(curl 오류 7, `-w "%{http_code}"` 형식으로 보면 `000`). `open-web-8082` 는 `200 OK` 였다. 추가 확인으로 `127.0.0.1:8081` 은 `200 OK` 였다.
- (다) 🔍 `closed-web-8081` 은 `127.0.0.1` 로 접속하면 열려 있는데 `내주소` 로는 거부되는 이유는 무엇인가요? 다른 PC가 접속하는 경우와 어떻게 같은가요?
  - 쓸 내용: ① 127.0.0.1 로는 열리는 이유 ② 내주소로는 거부되는 이유 ③ 다른 PC가 접속하는 경우와 같은 점
  - 답: 호스트 포트 8081이 `127.0.0.1` 에만 바인딩되어 있어 내 PC 안에서 localhost로 요청하면 컨테이너로 전달된다. `192.168.100.127` 같은 네트워크 주소에는 바인딩되지 않아 그 주소로는 연결되지 않는다. 다른 PC가 서버 PC의 네트워크 주소로 접속할 때도 localhost 바인딩은 그 요청을 받지 않으므로 접속할 수 없다.
- (라) 🔍 사내 PC에서 접속되면 안 되는 관리용 서버를 켠다면 `-p` 를 어떻게 쓰고, 이것이 4일 차의 어떤 원칙과 같은가요?
  - 쓸 내용: ① -p 에 쓸 형태 ② 같은 생각을 말하는 4일 차 원칙
  - 답: `-p 127.0.0.1:호스트포트:컨테이너포트` 형태로 localhost에만 게시한다. 필요한 연결만 명시적으로 허용하고 나머지는 차단하는 4일 차 방화벽의 허용 목록(기본 거부) 원칙과 같다.
- (마) 🔍 `docker inspect` 결과에서 두 서버의 `HostIp` 는 각각 무엇이고, `PORTS` 열의 어느 표시와 같은 뜻인가요?
  - 쓸 내용: ① closed-web-8081 의 HostIp ② open-web-8082 의 HostIp ③ 각각 `PORTS` 열의 어느 표시와 같은 뜻인지
  - 답: `closed-web-8081` 의 `HostIp` 는 `127.0.0.1` 로, `PORTS` 의 `127.0.0.1:8081->80/tcp` 와 일치한다. `open-web-8082` 의 `HostIp` 는 빈 문자열로 특정 주소에 한정하지 않았으며, `PORTS` 의 `0.0.0.0:8082->80/tcp` 와 `[::]:8082->80/tcp` 표시처럼 IPv4·IPv6 모든 주소에 게시된 설정이다.
- (바) 🔍 `open-web-8082` 의 비밀번호가 `docker exec` 로 그대로 읽혔습니다. 왜 문제이고, 비밀번호를 환경변수에 넣을 때 어떻게 다뤄야 하나요?
  - 쓸 내용: ① 읽힌 값 ② 왜 문제인지 ③ 다룰 때 지킬 것 두 가지 이상
  - 답: `docker exec open-web-8082 env` 에서 `DB_PASSWORD` 의 실습용 값이 그대로 출력됐다. 컨테이너에 접근할 수 있는 사용자나 권한 있는 도구가 환경변수를 읽을 수 있어, 실제 비밀번호를 넣으면 노출될 수 있다. 실습용 값만 사용하고 실제 비밀번호를 명령줄·로그·보고서에 기록하지 않는다. 운영 환경에서는 환경변수만으로 비밀이 보호된다고 여기지 말고 Docker secrets나 승인된 비밀 관리 시스템에서 주입·관리하며, 접근 권한과 수명을 제한하고 노출이 의심되면 교체한다.
- (사) 🔍 `whoami` 결과는 무엇이고, 이 서버가 침해되면 왜 위험이 커지나요? 6일 차 최소권한과 어떻게 이어지나요?
  - 쓸 내용: ① whoami 결과 ② 위험이 커지는 이유 ③ 최소권한과 이어지는 점
  - 답: `docker exec open-web-8082 whoami` 결과는 `root` 였다. 이는 `docker exec` 로 실행한 명령이 컨테이너 안에서 root로 실행됐다는 뜻이다. 이 권한으로 컨테이너 안의 파일·프로세스에 더 큰 영향을 줄 수 있어 침해 시 피해가 커질 수 있다(단, 이 결과만으로 nginx 작업 프로세스도 root라는 뜻은 아니다). 6일 차 최소권한 원칙에 따라 서비스와 관리 명령은 필요한 권한만 가진 전용 비-root 사용자로 실행하고 불필요한 권한을 제한해야 한다.

### 문제 2-2 · 알림 B · C 확인 — 응답이 없는 서버와 연달아 남은 404 읽기

- (가) 🔍 `wrongport-web-8084` 가 `Up` 인데 응답이 `000` 인 원인은 무엇인가요? `PORTS` 값, `docker logs` 에 요청 줄이 있었는지, `compare-web-8085` 와 비교한 결과를 근거로 적어 주세요.
  - 쓸 내용: ① 원인 ② `PORTS` 값 ③ `docker logs` 에 요청 줄이 있었는지 ④ `compare-web-8085` 와 비교한 결과
  - 답: `wrongport-web-8084` 는 `Up` 이지만, `PORTS` 는 `0.0.0.0:8084->8080/tcp` 와 `[::]:8084->8080/tcp` 였다. nginx 컨테이너는 기본적으로 80번 포트에서 요청을 받는데, 이 설정은 컨테이너의 8080번으로 전달하므로 요청이 nginx에 도달하지 않아 `000` 이 나왔다. `docker logs wrongport-web-8084` 에는 시작 메시지는 있었지만 요청의 `GET` 접속 기록은 없었다. 비교 서버는 `8085->80/tcp` 로 연결되어 `200` 을 반환했고, 로그에 `GET / HTTP/1.1` 과 `200` 이 기록됐다. 따라서 원인은 컨테이너 내부 포트 설정 오류다.
- (나) 🔍 `probe-web-8087` 의 접속 기록은 장애 · 위협 · 접근통제 중 무엇인가요? 출처 · 시각 · 경로 · 프로그램 중 세 가지 이상을 근거로 적고, 10/19(월)의 `favicon.ico` `404` 와 무엇이 다른지 적어 주세요.
  - 쓸 내용: ① 유형 ② 근거 세 가지 이상 ③ `favicon.ico` 404 와의 차이
  - 답: 유형은 **위협 의심(경로 탐색 시도)** 이다. 접속 로그에는 출처 `172.17.0.1`, 시각 `[21/Oct/2026:02:41:22 +0000]`, 경로 `/admin`, `/login`, `/.env`, `/wp-login.php`, `/backup.zip`, 프로그램 `curl/8.21.0` 이 기록됐고, 다섯 경로가 모두 `404` 였다. 이 실습에서는 내가 실행한 curl 요청이므로 실제 외부 공격이 발생한 증거는 아니며, `172.17.0.1` 도 Docker 네트워크를 거친 실습 요청의 출처로 봐야 한다. `favicon.ico` 404는 브라우저가 아이콘을 찾다가 한 번 실패한 일반적인 요청일 수 있지만, 여기서는 같은 시각에 관리·비밀 파일과 관련된 여러 경로를 연속 요청한 점이 다르다. 로그만으로 악의적 의도를 확정하지는 않는다.
- (답장) 보안 담당에게 보낼 답장을 씁니다. A · B · C 마다 유형 · 확인한 근거 · 먼저 할 일을 적어 주세요.
  - 쓸 내용: A · B · C 마다 ① 유형 ② 확인한 근거(`PORTS` 값 · 응답 번호 · 기록 줄) ③ 먼저 할 일
  - 답: **A — 접근통제 점검 필요:** `open-web-8082` 의 `PORTS` 는 `0.0.0.0:8082->80/tcp` 및 `[::]:8082->80/tcp`, `docker inspect` 의 `HostIp` 는 빈 값이었고 내 PC IP로 접속해 `200` 을 확인했습니다. 모든 인터페이스에 포트가 게시된 설정이므로, 의도한 공개 범위를 확인하고 사내 PC에서 접속되면 안 되는 서버라면 컨테이너를 중지한 뒤 localhost 바인딩 또는 승인된 방화벽 규칙으로 제한하겠습니다. 다른 PC에서의 실제 접속 여부는 별도로 검증해야 합니다. **B — 장애/설정 오류:** `wrongport-web-8084` 는 `Up` 이었지만 `8084->8080/tcp` 였고 응답은 `000`, 로그에 `GET` 줄이 없었습니다. `compare-web-8085` 는 `8085->80/tcp` 에서 `200` 과 `GET` 로그가 확인됐습니다. 컨테이너 포트 매핑을 실제 서비스 포트인 80으로 수정하고 다시 검사하겠습니다. **C — 위협 의심/경로 탐색:** 같은 초에 `/admin`, `/login`, `/.env`, `/wp-login.php`, `/backup.zip` 요청 다섯 건이 출처 `172.17.0.1`, 프로그램 `curl/8.21.0` 으로 기록됐고 모두 `404` 였습니다. 이번에는 실습 중 직접 발생시킨 요청이므로 외부 위협으로 보고하지 않으며, 실제 환경에서 반복 관찰되면 로그를 보존하고 출처와 주변 요청을 확인한 뒤 정책에 따라 차단·조사하겠습니다.
- 이 교시에서 새로 알게 된 것 하나를 적어 주세요.
  - 쓸 내용: 자유롭게
  - 답: 컨테이너가 `Up` 이어도 호스트 포트와 컨테이너에서 실제로 서비스가 듣는 포트가 다르면 요청은 서버에 도달하지 않을 수 있다. `PORTS` 설정과 접속 로그를 응답 코드와 함께 확인해야 원인을 구분할 수 있다.
