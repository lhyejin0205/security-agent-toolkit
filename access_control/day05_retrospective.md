# 3과목 총정리 (이름 · 2026-11-02(월))

## 상황 1 · 새 직원이 들어옴 (본보기)
- 원인: 데이터 문제입니다. hana 가 입사했는데 `users.json` 에 hana 가 아직 없습니다. 시스템은 사용자 파일에 없는 사람의 요청을 모두 「등록되지 않은 사용자」로 거부합니다.
- 고칠 파일: `config/users.json`
- 어떻게 고치나요: 새로 넣습니다. hana 를 `"hana": {"role": "sales", "employed": true}` 로 `users.json` 에 적습니다. `role` 은 hana 가 맡을 일에 맞는 역할로 정합니다.
- 고친 뒤 확인: hana 의 요청을 다시 판정해서 「등록되지 않은 사용자」가 사라지는지 봅니다.

## 상황 2 · 퇴사자 계정으로 요청이 계속 들어옴 (본보기)
- 원인: 데이터가 정리되지 않았습니다. dami 는 퇴사했는데 dami 의 항목이 `users.json` 에 그대로 남아 있어서 같은 시도가 계속 들어옵니다. `employed` 가 `false` 이면 요청은 거부되지만, 남은 항목 때문에 퇴사자 계정 점검에는 계속 걸립니다.
- 고칠 파일: `config/users.json`
- 어떻게 고치나요: dami 의 `"employed"` 가 `true` 로 남아 있다면 먼저 `false` 로 바꿉니다. 이미 `false` 이면 그대로 두고, dami 의 항목 전체를 `users.json` 에서 지웁니다.
- 고친 뒤 확인: 같은 요청이 「등록되지 않은 사용자」로 거부되고, 퇴사자 계정 점검이 통과로 바뀌는지 봅니다.
- 더 써 보고 싶은 것(선택): `check_permission` 이 퇴사 여부를 역할 확인보다 먼저 보는 이유는 무엇일까요? 퇴사 여부를 먼저 확인하지 않으면 퇴사한 사람이 역할 권한으로 허용될 수 있기 때문입니다.

## 상황 3 · 다른 팀 업무를 잠시 지원함
- 원인: 기간이 정해진 지원이라면 사람의 업무상 필요입니다. seoyeon 의 `sales` 역할에는 `SETTLE:QUERY` 가 없지만, 월말 정산 대조를 잠시 도우려면 그 권한이 필요합니다. 반대로 지원이 끝났는데 지난 예외가 남은 경우는 데이터 정리 문제입니다. 업무 자체가 영구히 바뀐 경우에는 역할을 바꾸어야 합니다.
- 고칠 파일: 기간제 지원은 `config/exceptions.json`, 만료된 예외 정리는 같은 파일, 영구적인 역할 변경은 `config/users.json` 입니다.
- 어떻게 고치나요: 기간제 지원은 사용하지 않은 다음 `id`, 사용자, 권한, 지원 종료 시각을 포함한 예외를 새로 추가하고 이유를 적습니다. 지원이 끝난 뒤에는 만료된 예외를 삭제합니다. 업무가 계속 바뀐 경우에는 예외를 반복해서 만들지 말고 사용자의 `role` 을 새 업무에 맞게 바꿉니다.
- 고친 뒤 확인: 지원 기간에는 요청이 예외 번호와 함께 허용되고 만료 시각부터는 허용되지 않는지 확인합니다. 만료 예외 점검도 다시 실행합니다. 역할을 바꾼 경우에는 새 역할의 권한은 허용되고 이전 역할의 권한은 더 이상 허용되지 않는지 확인합니다.
- 더 써 보고 싶은 것(선택): 퇴사자는 예외 확인 전에 거부되므로 예외가 남았다고 요청이 허용되는 것은 아니지만, 점검과 데이터 정리를 위해 예외도 별도로 제거해야 합니다.

## 상황 4 · 새 권한이 필요함
- 원인: 권한 부여의 승인과 기록 절차가 필요한 상황입니다. 요청자가 원하는 권한을 담당자가 파일에서 바로 추가하면 누가 언제 왜 승인했는지 남지 않고, 자기 요청을 스스로 승인할 위험도 있습니다.
- 고칠 파일: 요청·검토·부여 절차인 `req_create.py`, `req_review.py`, `req_grant.py`; 처리 기한이 현실과 맞지 않을 때만 `config/sla.json` 입니다.
- 어떻게 고치나요: 요청서를 만들고(`reviewing`), 요청자와 다른 검토자가 승인한 뒤(`approved`), 승인된 요청만 부여합니다(`granted`). 반려하면 `rejected` 로 둡니다. 기한을 넘긴 요청은 먼저 찾아 담당자에게 알리고, 4시간 기준이 실제 업무와 맞지 않는다는 근거가 있을 때만 SLA 값을 바꿉니다.
- 고친 뒤 확인: 요청 상태가 `reviewing` → `approved` → `granted` 순서로 바뀌고, 승인자가 기록되며, 승인 전에는 권한이 부여되지 않는지 확인합니다. 요청자 본인의 승인은 거절되고 기한 초과 요청은 목록에 표시되는지도 확인합니다.
- 더 써 보고 싶은 것(선택): 검토자와 요청자를 분리하면 승인 절차가 독립적으로 작동하고 감사할 근거가 남습니다.

## 상황 5 · 안 쓰는 권한이 쌓임
- 원인: 불필요한 권한은 회수 후보를 찾는 정기 점검이 없으면 계속 남습니다. 다만 오랫동안 사용하지 않았다는 사실만으로 항상 불필요한 것은 아닙니다. 계절 업무나 비상시에만 쓰는 권한일 수 있고, 퇴사자 권한은 제외 목록에 있더라도 회수 대상이어야 합니다.
- 고칠 파일: 후보를 찾는 로직은 `review_unused.py`, 마지막 사용 이력은 `config/access_log.json`, 필요한 예외를 기록하는 곳은 `config/exclude_list.json` 입니다.
- 어떻게 고치나요: 90일을 초과해 사용하지 않은 권한과 사용 이력이 없는 권한을 후보로 검토합니다. 정말 불필요하면 회수 절차로 넘깁니다. 드물게 쓰지만 필요한 권한은 사용자·권한·이유를 제외 목록에 기록하고, 퇴사자의 권한은 제외하지 않고 회수 대상으로 둡니다.
- 고친 뒤 확인: 후보와 제외 항목이 분리되는지 확인합니다. 정확히 90일은 기준이 `> 90` 이므로 후보가 아니고, 91일은 후보인지 확인합니다. 사용 이력이 없는 권한도 후보로 나오되 유효한 제외 이유가 있으면 제외되는지, 퇴사자 권한은 회수 후보로 남는지도 봅니다.
- 더 써 보고 싶은 것(선택): 후보 목록은 자동 회수 명령이 아닙니다. 업무 필요와 예외 사유를 검토한 뒤 회수 승인을 진행해야 합니다.

## 상황 6 · 민감한 권한을 회수해야 함
- 원인: 권한을 잘못 회수하면 업무가 중단될 수 있으므로 영향도와 민감도를 보고 승인하는 절차가 필요합니다. 예외 권한은 지원 종료 후 정리가 필요하고, 퇴사자 역할은 여러 권한에 영향을 줄 수 있으며, 재직자의 공통 역할을 바꾸면 그 역할을 가진 모든 사용자에게 영향이 갑니다.
- 고칠 파일: 회수 후보와 방법은 `revoke_plan.py`, 승인 조건은 `revoke_approve.py` 와 `config/sensitive.json`, 실제 데이터는 대상에 따라 `config/exceptions.json`, `config/users.json`, `config/roles.json` 입니다.
- 어떻게 고치나요: 먼저 회수 계획을 만들고 민감한 권한이거나 영향이 2건 이상이면 보안 책임자의 승인을 받습니다. 승인 대기 중에는 실행하지 않습니다. 예외 권한은 해당 예외를 삭제하고, 퇴사자는 승인 후 역할을 해제하며, 재직자의 역할 권한을 뺄 때는 역할을 공유하는 사용자를 확인한 뒤 역할 권한 목록에서 제거합니다. 거절된 계획은 실행하지 않고 이유를 해결한 뒤 새로 승인받습니다.
- 고친 뒤 확인: 승인 대기·거절 상태에서는 권한이 그대로인지 확인하고, 승인된 계획만 실행되어 회수 이력이 남는지 확인합니다. 실행 뒤 해당 요청이 거부되는지, 같은 역할을 가진 다른 사용자에게 예상치 못한 영향이 없는지도 확인합니다.
- 더 써 보고 싶은 것(선택): 계획 → 승인 → 실행을 나누면 민감한 권한이나 큰 영향을 주는 회수를 검토 없이 적용하는 실수를 줄일 수 있습니다.

## 상황 7 · 새벽 외부 접속, 그리고 정상 직원이 계속 거부됨
- 원인: 시간·접속 위치 기준이 빠져 위험한 요청이 허용될 수도 있고, 반대로 실제 업무 방식과 맞지 않는 조건 때문에 정상 직원 요청이 거부될 수도 있습니다. 문제는 조건 규칙에 있을 수 있지만, 규칙을 완화하면 다른 사용자에게도 영향이 갑니다.
- 고칠 파일: `config/conditions.json`
- 어떻게 고치나요:
  - 케이스 A — 쓰기 권한 `SALES:CHANGE` 에 조건이 빠져 새벽 외부 요청이 허용된다면, 허용 업무 시간과 네트워크를 확인한 뒤 규칙을 추가합니다. 예: `{"permission": "SALES:CHANGE", "hours": [9, 18], "networks": ["office", "vpn"]}`.
  - 케이스 B — gaeun 의 정상적인 VPN 요청이 거부된다면 업무 절차와 접속 방식이 승인된 것인지 확인하고, 사실이라면 `ACCOUNT:CHANGE` 의 네트워크를 `["office"]` 에서 `["office", "vpn"]` 으로 수정합니다. `external` 은 추가하지 않습니다.
  - 케이스 C — 업무가 실제로 더 늦게 끝나 18시 이후에도 써야 한다면 승인된 업무 시간을 확인한 뒤 종료 시각을 조정합니다. 단순히 거부를 없애려고 시간을 넓히지는 않습니다.
- 고친 뒤 확인: 같은 사용자·권한·시간·네트워크 요청을 다시 판정합니다. 새벽 외부 쓰기 요청은 거부되고 승인된 VPN 요청은 허용되는지 확인하며, 규칙 변경으로 불필요하게 넓은 시간이나 `external` 접속까지 허용되지 않는지도 시험합니다. 시간 구간의 끝 시각은 포함되지 않는 점도 확인합니다.
- 더 써 보고 싶은 것(선택): `SALES:QUERY` 처럼 조건이 없는 권한은 기본 역할 판정을 따릅니다. 조회 권한에도 시간·위치 제한이 필요한지 위험과 업무 필요를 따져 별도 규칙을 정할 수 있습니다.

## 상황 8 · 매주 어긋남을 확인해야 함
- 원인: 사람이 로그를 세면 기준이 매번 달라지거나 누락될 수 있어 반복 가능한 점검·집계·보고 절차가 필요합니다. 거부율 경고 기준이 현실과 맞지 않는 것은 규칙 문제이고, 로그가 비어 있는 것은 서버나 수집 데이터 문제일 수 있습니다.
- 고칠 파일: 점검은 `checklist.py`, 집계는 `log_summary.py`, 보고서는 `weekly_report.py`, 기준은 `config/alert.json` 입니다. 로그가 비어 있으면 서버 상태와 로그 수집 경로를 확인합니다.
- 어떻게 고치나요: 퇴사자·만료 예외·부서와 역할 점검, 로그의 허용·거부 수와 사유별 집계, 주간 보고서 저장을 같은 절차로 실행합니다. 경고 기준이 실제 위험 수준과 맞지 않을 때만 근거와 함께 `deny_rate_limit` 을 수정합니다. 전체 요청 수가 0이면 거부율 0%를 안전으로 해석하지 말고 서버 가동과 로그 수집을 확인합니다.
- 고친 뒤 확인: 주간 실행에서 기대한 사용자·예외·로그 건수가 모이고, 보고서에 점검 결과·거부 사유·거부율·경고가 남는지 확인합니다. 경고 기준을 바꿨다면 같은 로그의 판정이 기준에 따라 바뀌는지 확인하되, 거부 건수 자체가 바뀐 것처럼 해석하지 않습니다. 수집 복구 뒤에는 요청 수가 다시 기록되는지 확인합니다.
- 더 써 보고 싶은 것(선택): 보고서는 확인과 조치를 돕는 자료이지, 점검 결과만으로 권한을 자동 회수하거나 로그가 없는 주를 안전하다고 증명하지는 않습니다.
