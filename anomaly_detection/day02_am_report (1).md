## 2교시 · 웹 서버 로그를 공통 이벤트로 바꾸기

### 문제 2-1 · 웹 서버 로그 한 줄을 공통 이벤트로 바꾸기

- (가) 실행한 출력 전체를 붙여 넣고, 정규화한 이벤트 수와 읽기 실패한 줄 수, 성공과 실패 개수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 정규화한 이벤트 수와 읽기 실패한 줄 수 ③ 성공 · 실패 개수
  - 답:

```
--- 단계 1: 정규화한 이벤트 28 개 · 읽기 실패 2 줄
{'time': '2026-11-02 09:01:05', 'source': 'web', 'user': None, 'ip': '198.51.100.21', 'action': 'GET /', 'result': '성공', 'raw': '198.51.100.21 - - [02/Nov/2026:09:01:05 +0900] "GET / HTTP/1.1" 200 1204 "-" "Mozilla/5.0"'}
--- 단계 2: 처음 나오는 실패 이벤트
{'time': '2026-11-02 09:12:03', 'source': 'web', 'user': None, 'ip': '203.0.113.50', 'action': 'POST /login', 'result': '실패', 'raw': '203.0.113.50 - - [02/Nov/2026:09:12:03 +0900] "POST /login HTTP/1.1" 401 312 "-" "python-requests/2.31.0"'}
--- 단계 3: 성공 · 실패별 개수
{'성공': 15, '실패': 13}
```

- (나) 🔍 시각을 `02/Nov/2026:09:00:00 +0900` 모양 그대로 문자열로 정렬하면 12월 1일 요청(`01/Dec/2026:…`)과 11월 2일 요청(`02/Nov/2026:…`) 중 어느 쪽이 앞에 놓일지 예상하고, 공통 모양(`2026-11-02 09:00:00`)으로 바꾸면 무엇이 달라지는지 이유와 함께 적어 주세요.
  - 쓸 내용: ① 어느 쪽이 앞에 놓일지 ② 공통 모양으로 바꾸면 달라지는 점과 그 이유
  - 답: 원래 모양을 문자열로 정렬하면 날짜의 월·연도보다 일(day)이 먼저 비교되므로 `01/Dec/2026:…`(12월 1일)이 `02/Nov/2026:…`(11월 2일)보다 앞에 놓입니다. `2026-12-01 …`과 `2026-11-02 …`처럼 연-월-일 순서로 바꾸면 큰 단위부터 비교되어 문자열 정렬 결과가 실제 시간순과 같아지고, 11월 2일이 12월 1일보다 앞에 놓입니다.

- (다) 🔍 이벤트에 원래 로그 줄(`raw`)을 그대로 남겨 두는 이유는 무엇인가요? 정규화하면 사라지는 정보를 한 가지 예로 들어 함께 적어 주세요.
  - 쓸 내용: ① `raw` 를 남겨 두는 이유 ② 정규화하면 사라지는 정보의 예
  - 답: 정규화한 값이 원래 로그와 맞는지 확인하고, 분석 결과를 추적하거나 파서 오류를 조사할 수 있도록 원문을 남깁니다. 예를 들어 상태 코드 `401`은 공통 이벤트에서 단순히 `실패`로 바뀌어 정확한 코드가 사라지지만, `raw`를 보면 원래 코드와 응답 크기, 사용자 에이전트 등을 확인할 수 있습니다.

## 3교시 · 판정 서버 로그와 SaaS 로그를 공통 이벤트로 바꾸기

### 문제 3-1 · 판정 서버 로그와 SaaS 로그를 공통 이벤트로 바꾸기

- (가) 실행한 출력 전체를 붙여 넣고, 판정 서버와 SaaS 이벤트의 수와 성공 · 실패별 개수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 판정 서버 이벤트 수와 성공 · 실패별 개수 ③ SaaS 이벤트 수와 성공 · 실패별 개수
  - 답:

```
--- 단계 1: 판정 서버 이벤트 15 개
{'성공': 6, '실패': 9}
--- 단계 2: SaaS 이벤트 14 개
{'실패': 1, '성공': 13}
--- 단계 3: 각 로그의 첫 이벤트
{'time': '2026-11-02 09:40:00', 'source': 'server', 'user': 'seoyeon', 'ip': None, 'action': 'SALES:QUERY', 'result': '성공', 'raw': '{"time": "2026-11-02T09:40", "user": "seoyeon", "permission": "SALES:QUERY", "network": "office", "allowed": true, "reason": "역할 권한"}'}
{'time': '2026-11-02 02:14:08', 'source': 'saas', 'user': 'jiwoo', 'ip': '203.0.113.80', 'action': 'login', 'result': '실패', 'raw': {'time': '2026-11-02 02:14:08', 'account': 'jiwoo@a-corp.example', 'event': 'login', 'ip_address': '203.0.113.80', 'outcome': 'failure'}}
```

- (나) 🔍 판정 서버 로그에는 접속 주소가 없어서 `ip` 를 `None` 으로 두었습니다. `None` 대신 가짜 주소 `0.0.0.0` 을 넣으면 주소별로 셀 때 어떤 문제가 생길까요? 이유도 함께 적어 주세요.
  - 쓸 내용: ① 가짜 주소를 넣으면 생기는 문제 ② 그 이유
  - 답: 주소가 없는 판정 서버 이벤트들이 모두 실제 주소인 것처럼 `0.0.0.0` 하나로 집계됩니다. 그러면 주소별 요청 수가 부풀고, 서로 다른 사용자의 이벤트를 같은 접속지에서 온 것처럼 오해해 공격 출처를 잘못 판단하거나 탐지 결과에 오탐·누락이 생길 수 있습니다. `None`으로 두면 주소 정보가 관측되지 않았다는 사실을 보존하고 실제 IP 통계와 구분할 수 있습니다.

- (다) 🔍 정규화하면서 공통 이벤트의 키에 들어가지 않은 정보를 판정 서버 로그에서 찾아 적고, 그 정보를 나중에 어디서 찾을 수 있는지 적어 주세요.
  - 쓸 내용: ① 공통 이벤트의 키에 들어가지 않은 정보 ② 그 정보를 나중에 찾을 수 있는 곳
  - 답: 판정 서버 로그의 `network`(예: `office`, `vpn`)와 `reason`(예: `역할 권한`, `업무 시간 밖`)은 공통 이벤트 키로 옮기지 않았습니다. 원래 JSON 문자열이 `raw`에 보관되어 있으므로 해당 이벤트의 `raw`를 확인하면 이 정보를 다시 찾을 수 있습니다.

## 4교시 · 세 로그를 하나로 합쳐 시간순으로 저장하기

### 문제 4-1 · 세 로그의 이벤트를 합쳐 시간순으로 저장하기

- (가) 실행한 출력 전체를 붙여 넣고, 소스별 이벤트 수와 `user` · `ip` 가 비어 있는 이벤트 수, 저장된 이벤트 수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 소스별 이벤트 수 ③ `user` · `ip` 가 비어 있는 이벤트 수 ④ 저장된 이벤트 수
  - 답:

```
--- 단계 1: 소스별 이벤트 수
{'saas': 14, 'web': 28, 'server': 15}
--- 단계 2: 값이 None 인 이벤트 수
user 가 비어 있는 이벤트 28 개
ip 가 비어 있는 이벤트 15 개
--- 단계 3: gaeun 의 이벤트를 시간순으로
2026-11-02 10:05:00 server ACCOUNT:CHANGE 실패
2026-11-02 10:09:00 server ACCOUNT:CHANGE 실패
2026-11-02 10:12:55 saas login 성공
2026-11-02 10:14:00 server ACCOUNT:CHANGE 실패
2026-11-02 16:10:00 server SALES:QUERY 성공
--- 단계 4: 저장한 파일 normalized_events.json
저장된 이벤트 57 개
```

- (나) 🔍 단계 3의 gaeun 이벤트를 시간순으로 보고, 서로 다른 소스에서 나온 이벤트가 어떻게 이어지는지 적고, 로그를 따로 볼 때와 무엇이 달라지는지 적어 주세요.
  - 쓸 내용: ① 여러 소스에 걸친 이벤트의 순서 ② 로그를 따로 볼 때와 달라지는 점
  - 답: 시간순으로 보면 판정 서버에서 `ACCOUNT:CHANGE` 실패가 10:05와 10:09에 발생하고, 그 사이에 SaaS 로그인 성공(10:12:55)이 이어진 뒤 판정 서버의 같은 권한 요청 실패(10:14)가 다시 나타납니다. 이후 16:10에는 판정 서버에서 `SALES:QUERY`가 성공합니다. 로그를 따로 보면 각 서비스 안의 기록 순서만 볼 수 있지만, 합쳐 정렬하면 서로 다른 시스템의 이벤트를 한 사용자 기준으로 연결해 로그인과 권한 요청의 시간 관계를 파악할 수 있습니다.

- (다) 🔍 `user` 가 비어 있는 이벤트가 28개입니다. 어느 로그(소스)의 이벤트이고 왜 비어 있는지 적어 주세요. 그리고 사용자 이름별로 개수를 세면 이 28개가 어떻게 될지 예상해 적어 주세요.
  - 쓸 내용: ① 비어 있는 이벤트의 로그(소스)와 이유 ② 사용자 이름별로 셀 때의 예상
  - 답: `user`가 비어 있는 28개는 모두 웹 서버(`web`) 이벤트입니다. 웹 서버 로그에는 사용자 이름이 없어 정규화할 때 `user`를 `None`으로 두었습니다. 사용자 이름별 집계에서는 이 28개를 실제 사용자에게 나눠 연결할 수 없으며, `None`을 별도 항목으로 포함하면 `None: 28개`로 모이고, 비어 있는 값을 제외하는 집계에서는 사용자별 결과에 나타나지 않습니다.
