## 2교시 · 점수 파일의 사실만 Gemini API 에 보내 대상별 AI 요약 받기

### 문제 2-1 · AI 에게 사실만 보내 대상별 요약 받기

- (가) 실행한 출력 전체를 붙여 넣고, 요약한 대상 수와 `(요약 실패 …)` 가 나온 대상 수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 요약한 대상 수 ③ `(요약 실패 …)` 가 나온 대상 수
  - 답: 아래는 `call_llm` 을 로컬에서 모의 응답으로 바꿔 실행한 출력입니다. 실제 Gemini API 호출은 하지 않았습니다. 요약 대상은 3명이고, 실패 대체 문장이 나온 대상은 0명입니다.

```
--- 단계 1: 불러온 점수 기록 5 건
--- 단계 2: 요약할 대상 3 명 (최대 3 명)
high dami 60
mid seoyeon 45
mid gaeun 40
--- 단계 3: AI 에게 보내는 글 (seoyeon)
당신은 보안 관제 담당자를 돕는 도우미입니다. 아래 [사실]만 사용해 한국어 두 문장 이하로 요약하세요. [사실]에 없는 내용은 지어내지 말고, 공격이라고 단정하지 마세요. 먼저 확인할 것을 한 가지 제안하세요.
[사실] 대상: seoyeon / 등급: mid / 점수: 45점 / 탐지된 내용: 평소와 다른 IP 에서 SaaS 에 접속함; SaaS 에서 파일을 한꺼번에 많이 내려받음
--- 단계 4: Gemini API 를 활용한 AI 요약
dami : dami: Former employee account made a server request. Check the account request log first.
seoyeon : seoyeon: SaaS access came from an unusual IP and many files were downloaded. Check the IP and download records first.
gaeun : gaeun: The server rejected a rule-allowed request, and events appeared in separate logs. Check the server response and related logs first.
```

- (나) 🔍 단계 3 의 지시문이 AI 에게 하지 말라고 한 것 두 가지를 찾고, 각각 하면 왜 위험한지 적어 주세요.
  - 쓸 내용: ① 하지 말라고 한 것 두 가지 ② 각각 하면 위험한 이유
  - 답: 첫째, `[사실]` 에 없는 내용을 지어내지 말라고 했습니다. 없는 내용을 덧붙이면 담당자가 실제 기록과 다른 정보에 근거해 조사하거나 대응할 수 있기 때문입니다. 둘째, 공격이라고 단정하지 말라고 했습니다. 점수와 탐지 규칙만으로 공격 여부를 확정하면 정상 활동을 공격으로 오판해 잘못된 대응을 할 수 있기 때문입니다.

- (다) 🔍 단계 4 의 요약 하나를 골라 2.1 의 점수 기록 표(대상 · 점수 · 등급 · 탐지된 규칙)와 비교해, 표에 없는 내용이 들어 있는지 적어 주세요. 있으면 어떤 문장인지와 지시문을 어떻게 고칠지, 없으면 없다고 쓰고 탐지된 규칙이 모두 문장에 들어갔는지 적어 주세요.
  - 쓸 내용: ① 고른 요약의 대상 ② 표에 없는 내용이 있는지 ③ 있으면 그 문장과 지시문을 고칠 방법, 없으면 탐지된 규칙이 모두 들어갔는지
  - 답: seoyeon 의 모의 요약을 골랐습니다. 표에 있는 mid 등급, 45점, `평소와 다른 IP`, `대량 다운로드`만 요약했고 표에 없는 사실은 없습니다. 두 탐지 내용이 모두 들어갔습니다. 실제 AI 응답도 사실에 맞는지 확인하려면, 표의 사실만 사용하고 근거가 없는 내용은 덧붙이지 말라는 지시문을 유지해야 합니다.

## 3교시 · 탐지부터 보고서 저장까지 pipeline.py 로 한 번에 실행하기

- (가) 실행한 출력 전체를 붙여 넣고, 보고서 파일의 `event_count` · `finding_count` 값과 `records` · `summaries` 의 건수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② `event_count` ③ `finding_count` ④ `records` 건수 ⑤ `summaries` 건수
  - 답: `event_count` 는 57, `finding_count` 는 8, `records` 는 5건, `summaries` 는 3건입니다. AI 호출 실패는 0건이었습니다.

```
--- 단계 1: 읽은 이벤트 57 개
--- 단계 2: 탐지된 규칙 8 건 → 점수 기록 5 건을 day03_risk_scores.json 에 저장
--- 단계 3: Gemini API 를 활용한 AI 요약 3 건 (실패 0 건)
dami : 대상 'dami'는 등급 'high', 점수 60점으로 퇴사한 사람의 계정을 통해 서버에 요청한 내역이 탐지되었습니다. 보안 관제를 위해 해당 계정의 실제 접속 주체와 요청 목적을 먼저 확인하는 것을 제안합니다.
seoyeon : seoyeon 대상자의 mid 등급(45점)에서 평소와 다른 IP의 SaaS 접속 및 대량의 파일 다운로드가 탐지되었습니다. 정상적인 업무 행권인지 본인에게 먼저 확인하는 것을 제안합니다.
gaeun : 대상 'gaeun'(중급, 40점)은 규칙상 허용되는 요청에 대해 서버가 거절한 이력과 짧은 시간 내 다른 로그에서 이벤트가 확인되었습니다. 공격 여부를 판단하기 위해 해당 사용자의 최근 요청 내용과 서버 거절 사유를 먼저 확인하시기 바랍니다.
--- 단계 4: 보고서를 anomaly_detection_report_2026-11-02.json 에 저장
--- 단계 5: 확인할 순서
high dami 60
mid seoyeon 45
mid gaeun 40
mid jiwoo 35
low 198.51.100.90 30
```

- (나) 🔍 점수와 등급은 코드가 정하고 AI 에게는 요약만 시킨 이유를 적어 주세요. 단계 5 의 확인할 순서와 단계 3 의 요약을 근거로 쓰세요.
  - 쓸 내용: ① 점수와 등급을 코드가 정한 이유 ② 단계 5 와 단계 3 에서 찾은 근거
  - 답: 점수와 등급은 정해진 탐지 규칙과 가중치로 코드가 계산해야 결과가 일관되고, AI 요약이 달라져도 위험도 판단이 흔들리지 않습니다. 단계 5에서는 코드가 점수 순서대로 dami(high, 60), seoyeon(mid, 45), gaeun(mid, 40), jiwoo(mid, 35), IP(low, 30)를 출력합니다. 단계 3의 AI는 상위 세 대상의 이미 정해진 등급·점수와 탐지 사실을 문장으로 요약할 뿐, 점수나 등급을 바꾸지 않습니다.

- (다) 🔍 AI 호출이 실패해도 파이프라인이 멈추지 않고 대체 문장을 쓰게 만든 이유를 적어 주세요. 대체 문장이 들어간 대상을 담당자가 어떻게 처리해야 하는지도 적어 주세요.
  - 쓸 내용: ① 실패해도 멈추지 않게 만든 이유 ② 대체 문장이 들어간 대상을 처리하는 방법
  - 답: API 오류나 호출 한도가 있어도 나머지 대상의 분석과 보고서 저장이 완료되어야 자동 실행 결과가 남고, 담당자가 확인을 이어갈 수 있기 때문입니다. 실패 문장이 나온 대상은 AI 요약을 근거로 삼지 말고 보고서의 `records`에서 점수·등급·탐지된 규칙을 직접 확인한 뒤 원본 로그와 대조해 조사합니다. 이번 실행은 실패가 0건이라 대체 문장은 나오지 않았습니다.

## 4교시 · 4과목 총정리: 상황마다 원인과 고치는 방법 정리하기

### 문제 4-1 · 상황 8개의 원인과 고치는 방법을 내 말로 정리하기

**상황 정리** — 상황 1 · 2 · 3 · 4 · 7 · 8 중 4개 이상 씁니다. 상황 5 · 6 은 본보기입니다.

#### 상황 1 · 설정 파일 주소를 연달아 요청했는데 「의심」이 아니라 「오류」로 분류됨
- 원인: 규칙 문제입니다. `log_classify.py` 의 `is_suspicious` 는 상태 코드 401 · 403 이거나 경로에 `/admin` 이 있을 때만 의심으로 분류합니다. 세 요청은 모두 404 이고 `/admin` 경로도 아니어서 `is_error` 에서 오류로만 분류됩니다.
- 고칠 파일: `log_classify.py` (`is_suspicious`)
- 어떻게 고치나요: 조건을 수정해 경로에 `/.env` · `/wp-login` · `/phpmyadmin` 중 하나가 포함되면 의심으로 분류하도록 추가하고, 기존 조건과 `or` 로 연결합니다. 반복 스캔을 더 일반적으로 잡으려면 같은 IP 가 없는 주소를 연속 요청한 횟수를 세는 규칙도 추가합니다.
- 고친 뒤 확인: 같은 로그를 다시 분류해 198.51.100.90 의 세 요청이 「의심」에 들어가는지 확인합니다. 예시 규칙 수정 후 분류별 개수는 정상 15 · 오류 2 · 의심 11 입니다.
- 담당자가 가장 먼저 할 일(선택): 같은 IP 에서 같은 시간대에 다른 요청이 더 있었는지, 성공(200)한 요청이 있었는지 접속 기록을 확인합니다.

#### 상황 2 · 로그 30줄이 이벤트 28개가 됨
- 원인: 데이터 문제입니다. 원본 로그 30줄 중 2줄은 잘렸거나 형식이 깨져 큰따옴표가 부족합니다. `normalize_web` 이 그 줄을 `None` 으로 반환해 이벤트로 만들지 않으므로 웹 이벤트가 28개가 됩니다.
- 고칠 파일: 정규화 코드는 의도대로 동작하므로 코드 수정은 하지 않습니다. 원본 웹 로그를 만든 서버의 로그 생성 설정을 확인합니다.
- 어떻게 고치나요: 먼저 실패한 두 줄의 원문을 확인하고, 서버가 로그를 쓰는 중 줄이 잘린 원인을 찾아 로그 생성 쪽을 수정합니다. 이 샘플에서는 원인을 확인하기 전 정규화 코드를 바꾸지 않습니다.
- 고친 뒤 확인: 정규화한 이벤트 수와 읽기 실패 줄 수를 더해 원본 30줄과 같은지 확인합니다. 현재는 28개 + 실패 2줄 = 30줄입니다.
- 담당자가 가장 먼저 할 일(선택): 읽히지 않은 두 줄을 원본 로그에서 찾아 서버가 기록을 쓰는 도중 끊겼는지 확인합니다.

#### 상황 3 · 웹 서버 로그에서 사용자를 알 수 있는 요청이 1개뿐
- 원인: 데이터 문제입니다. 웹 서버 로그에는 사용자 이름 대신 IP만 있고, IP 를 사용자에게 연결할 성공한 SaaS 로그인 기록도 대부분 없습니다. 그래서 실패 요청 13개 중 사용자까지 알 수 있는 것은 1개뿐입니다.
- 고칠 파일: 케이스 A 는 웹 서버 로그 설정, 케이스 B 는 `risk_scores.py` 입니다.
- 어떻게 고치나요:
  - 케이스 A: 웹 서버 로그 설정에 로그인한 사용자 이름을 기록하는 항목을 추가합니다. 웹 서버가 사용자 정보를 전달받지 못하는 구성이라면 인증 시스템과 연동할 방법을 먼저 확인합니다.
  - 케이스 B: 사용자를 알 수 없는 요청은 임의의 사용자에게 붙이지 말고 IP 를 대상으로 점수를 기록합니다. 경로 스캔 IP처럼 `entity` 에 IP를 넣어 보존합니다.
- 고친 뒤 확인: 케이스 A 는 다시 분석해 사용자 정보가 붙은 웹 이벤트가 1개보다 늘었는지 확인합니다. 케이스 B 는 점수 기록의 `entity` 에 해당 IP 가 보이는지 확인합니다.
- 담당자가 가장 먼저 할 일(선택): 요청 IP 가 다른 로그나 인증 기록에 나타나는지 검색해 실제 사용자를 확인합니다.

#### 상황 4 · 두 로그에 나오는 seoyeon 이 연결되지 않음
- 원인: 규칙 문제입니다. `find_chains` 는 사용자의 첫 이벤트부터 마지막 이벤트까지 전체 시간이 `WINDOW_MINUTES`(60분) 이내여야 연결합니다. seoyeon 은 09:05부터 18:20까지 555분이라 제외되지만, 17:38 로그인부터 18:20 서버 거절까지는 42분입니다.
- 고칠 파일: `correlation.py` (`find_chains`)
- 어떻게 고치나요:
  - 케이스 A: `WINDOW_MINUTES` 를 600으로 바꾸면 이 샘플에서 seoyeon 이 555분 안의 사건으로 연결됩니다. 다만 하루 전체 이벤트가 한 사건으로 묶여 연결 기준의 의미가 약해질 수 있습니다.
  - 케이스 B: 전체 첫·마지막 시각만 비교하는 방식을 바꿔, 이웃한 이벤트 사이가 60분 이내로 이어지는 이벤트끼리 묶습니다.
- 고친 뒤 확인: 분석을 다시 실행해 seoyeon 이 연결된 사건에 나타나는지와 연결 사유의 시간 범위를 확인합니다. 케이스 A 에서는 `555분 안` 이 표시됩니다.
- 담당자가 가장 먼저 할 일(선택): seoyeon 의 17:38 로그인부터 18:20 서버 거절까지를 시간순으로 확인합니다.

#### 상황 5 · 협력사 사무실에서 접속한 정상 접속에 알림이 남 (본보기)
- 원인: 규칙 문제입니다. `SaaS 평소와 다른 IP` 규칙은 지난 접속 기록에 없는 IP 이면 모두 알림을 냅니다. 협력사 사무실 IP 203.0.113.80 에서 jiwoo(A4)와 seoyeon(A5)이 출장 · 외근 중에 접속했는데, 조사해 보니 모두 정상 접속이었습니다.
- 고칠 파일: `tuning.py` (`TRUSTED_IPS` 와 `apply_exception`)
- 어떻게 고치나요: 새로 넣고 뺍니다. 믿는 IP 리스트에 `203.0.113.80` 한 개를 넣고, `SaaS 평소와 다른 IP` 규칙의 알림 가운데 그 IP 에서 온 것만 알림 표에서 뺍니다. 다른 규칙의 알림(A3 · A6)은 같은 IP 여도 빼지 않습니다.
- 고친 뒤 확인: 오탐이 4개에서 2개로 줄었는지 보고, 빠진 알림 가운데 진짜 문제(`real` 이 `True`)가 0개인지 봅니다.
- 담당자가 가장 먼저 할 일(선택): 203.0.113.80 이 협력사 사무실 IP 가 맞는지 출장 · 외근 일정과 비교해 확인합니다.

#### 상황 6 · 로그인 규칙이 낸 알림이 평가에서 빠짐 (본보기)
- 원인: 데이터 문제입니다. 로그인 규칙이 낸 알림 A8 은 `login_alerts.json` 에 따로 저장돼 있고, 첫 평가에 쓴 `review_alerts.json` 의 알림 7개에는 들어 있지 않습니다. 평가는 알림 7개만 보고 「알림이 난 진짜 문제」를 세므로, A8 이 가리키는 P4 가 미탐으로 셉니다. 규칙은 알림을 이미 냈지만 평가에 들어가지 못했습니다.
- 고칠 파일: `final_check.py` (`merge_alerts`)
- 어떻게 고치나요: 새로 넣습니다. `pd.concat([alerts, login_alerts])` 로 두 알림 표를 위아래로 이어 붙인 뒤 합친 표로 평가합니다. A8 은 조사해 보니 진짜 문제(`real` 이 `True`)여서 오탐은 늘지 않습니다.
- 고친 뒤 확인: 미탐이 2개(P4 · P5)에서 1개(P5)로 줄고 오탐은 2개 그대로인지 봅니다.
- 담당자가 가장 먼저 할 일(선택): 203.0.113.50 이 로그인에 성공한 뒤 요청한 `/admin` · `/admin/users` 가 모두 403(접근 거부)이었는지, 그 뒤에도 요청이 이어졌는지 로그에서 확인합니다.

#### 상황 7 · 정산 조회 시도에는 알림이 나지 않음
- 원인: 규칙 문제입니다. `pick_suspicious` 는 한 사용자의 서버 실패가 `REPEAT_LIMIT`(3회) 이상일 때 확인 대상으로 삼습니다. seoyeon 의 실패는 `SETTLE:QUERY` 와 `SALES:CHANGE` 두 번뿐이라 알림 기준에 못 미쳐, 중요한 정산 조회 시도를 놓쳤습니다.
- 고칠 파일: `access_detection.py` (`pick_suspicious`)
- 어떻게 고치나요: 정산 조회처럼 중요한 권한 목록(예: `SETTLE:QUERY`)을 새로 정하고, 서버 실패 이벤트의 `action` 이 목록에 있으면 횟수와 관계없이 확인 대상으로 추가하는 규칙을 넣습니다. 한 번의 업무상 실수도 알림이 될 수 있으므로 중요 동작을 신중히 고릅니다.
- 고친 뒤 확인: 같은 이벤트로 다시 분석해 P5 가 확인 대상에 포함되는지 보고, 오탐과 미탐을 다시 계산해 오탐이 얼마나 늘었는지 확인합니다.
- 담당자가 가장 먼저 할 일(선택): seoyeon 에게 11:40 의 정산 조회가 업무상 요청이었는지 확인합니다.

#### 상황 8 · 서버가 같은 네트워크에 열려 있고, 지우면 접속 기록도 사라짐
- 원인: 운영 설정 문제입니다. 첫째, 컴포즈 `ports` 에 주소가 지정되지 않아 같은 네트워크의 다른 PC 에도 포트가 열려 있습니다. 둘째, 서버 로그 디렉터리가 로컬 폴더에 연결되지 않아 컨테이너를 지우면 기록도 사라집니다.
- 고칠 파일: `compose.secure.yaml`
- 어떻게 고치나요:
  - 케이스 A(접속 범위): `"8081:80"` 을 `"127.0.0.1:8081:80"` 으로 바꿔 `web2` 를 내 PC 에서만 접속할 수 있게 합니다. 다른 사람에게 공개할 `web1` 설정은 그대로 둡니다.
  - 케이스 B(접속 기록): `web2` 설정에 `volumes:` 를 추가하고 `- ./logs:/var/log/nginx` 를 넣어 로그를 내 PC 의 `logs` 폴더에 보존합니다.
- 고친 뒤 확인: 케이스 A 는 `docker compose ps` 에 `127.0.0.1:8081->80/tcp` 로 표시되는지 확인합니다. 케이스 B 는 컨테이너를 내린 뒤에도 `logs` 폴더에 `access.log` 가 남는지 확인합니다.
- 담당자가 가장 먼저 할 일(선택): 보존된 `logs/access.log` 에 내 PC 가 아닌 IP 의 요청이 있는지 확인합니다.
